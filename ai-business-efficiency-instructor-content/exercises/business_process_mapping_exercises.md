> このファイルから学習を始める場合は、[用語集](../glossary.md)も開いてください。**PoC（概念実証）**は本格導入前の小規模検証、**KPI**は目標への進み具合を測る指標、**CRM**は顧客情報・商談・対応履歴を管理する仕組み、**RAG**は関係資料を検索して回答材料にする仕組みです。

## この演習の目的

業務名を丸ごと「AI化」せず、開始・作業・判断・例外・承認・完了へ分解し、廃止、簡素化、通常の自動化、AI補助、人間判断を切り分けます。

## 準備：AIを使う2つの経路から選ぶ

この演習は一人で完了できます。ペアで相互確認する方法は任意です。次のうち、利用できる経路を一つ選びます。

| 経路 | 準備とルール |
|---|---|
| 個人学習 | 公式URL、利用規約、プライバシー設定、料金を最新の公式情報で確認し、本人が利用を認めた対話AIへ教材の架空データだけを入力する |
| 組織利用 | 組織が承認した対話AI、業務用アカウント、指定保存先、正式な相談先だけを使う |

この演習では、自分の初案と対話AIの案を比較する**AIの実操作が必須**です。承認済み対話AIを利用できない場合は、[共通準備](../setup/common_preparation.md)へ戻り、利用環境が整うまで演習を停止します。

## 演習の共通手順

1. **目的と成果物**を確認する。
2. **準備**として、使用経路と収録ファイルを確認する。
3. **手順付き例**だけを、説明を読みながら試す。
4. **自力課題**は、自己点検ガイドを開かずに作る。
5. **人による元資料照合**として、AI出力と元資料を自分で1項目ずつ比べる。
6. 詰まった場合だけ、末尾の**段階ヒント**を一つずつ開く。
7. 自力課題の後に**自己点検**ガイドと比べる。
8. 誤りまたは改善点を**最低1点修正**し、修正理由を残す。
9. **完了条件**と安全な終了を確認し、**次へ**進む。

## 共通ルール

- ケースはすべて架空です。実システムへの接続や外部送信はしません。
- 個人学習でも組織内学習でも、承認済み環境であっても教材に記載された完全な架空データだけを入力します。実際のメール、顧客名、社内文書、画面、数値、ログ等は使いません。
- ツールを先に選ばず、現行業務と問題を先に可視化します。
- 作業時間には確認、修正、差戻し、待ち時間を含めます。
- 高影響判断、外部送信、支払、削除、権限変更には人間承認を置きます。

## 使用ツールと開始前準備

- 基本ツール：本人または組織が利用を認めた対話AI（例：ChatGPT）と[業務分析シート](../templates/business_analysis_sheet.md)
- 準備手順：[AIツール共通準備](../setup/common_preparation.md)と[対話AIのアカウント準備](../setup/chat_ai_account_setup.md)
- 記録方法：Markdown、表計算、または印刷した業務分析シート。印刷物はAI案との比較や人間レビューの記録にだけ使う

個人学習では、本人が最新の公式条件、料金、データ設定を確認し、本人管理の承認済み対話AIを使います。ChatGPTは一例であり、別の承認済み対話AIでも構いません。入力は完全な架空データに限定します。

組織で学ぶ場合は、個人アカウントを新規登録せず、組織指定の承認済みツールだけを使います。承認済み対話AIを利用できない場合は業務分解の下書きまでにとどめ、利用環境が整うまで演習を停止します。

## 演習の共通進行

一人で、`現場担当`、`業務責任者`、`IT・セキュリティ担当`の三つの視点を順に切り替えて確認します。ペアやグループで役割を分ける方法は任意です。

1. **準備確認**：利用経路、架空データ、業務の開始・完了、入力禁止を確認する。
2. **自分の初案**：AIを使う前に、一つの業務を1行1動作へ分ける。
3. **AI案**：下の共通プロンプトで、分解案と不足情報の候補を出す。
4. **比較・修正**：自分の初案とAI案を比べ、採用・修正・却下と理由を残す。
5. **After設計**：廃止・簡素化・通常自動化・AI補助・人間判断を切り分け、確認・承認・手動代替を置く。
6. **人による元資料照合**：AI案を閉じ、三つの視点から、判断・例外・承認・手動代替を自分で確認する。
7. **振り返り**：Before／After、停止条件、AIを使わない判断を説明する。

現場担当の視点では実態と例外、責任者の視点では品質と承認、IT・セキュリティ担当の視点ではデータ・権限・運用を確認します。根拠のないAI化を見つけたら修正し、判断できない項目は無理に決めず、`要確認・確認先・確認期限`を記録します。

## 手順付き例：架空の定例報告を2動作へ分ける

まず、AIへ送る前の自分の初案として、次の小さな架空ケースを分解します。この後に必ずAI案を生成して比較します。

> 担当者は、承認済みの月次集計表を開き、決められた3項目を報告書へ転記する。転記後、責任者が元の集計表と照合し、承認したら完了する。

| No. | 現行作業 | 入力・出力 | 判断・例外 | 改善分類 | 改善後 | リスク・承認 |
|---:|---|---|---|---|---|---|
| 1 | 承認済み集計表から3項目を転記 | 集計表→報告書草案 | 元表が未承認なら停止 | 通常自動化またはAI補助 | 候補値と元セル位置を提示 | 転記元と値を人が照合 |
| 2 | 責任者が照合し承認 | 元表、草案→承認済み報告書 | 不一致なら差戻し | 人 | 承認判断は人のまま | 未承認の外部送信を禁止 |

この例では、`報告書作成`を一行で済ませず、転記と承認を分けています。また、AIを使う前に通常の自動化も候補にしています。同じ考え方で、以下の自力課題を一行一動作へ分けます。

## コピー用共通プロンプト

まずAIを使わず自分の初案を作ってから、次を承認済み対話AIへコピーします。`【架空ケース】`には、この教材に記載されたケース文だけを貼ります。

```text
あなたは業務分析の補助者です。次の文章は研修用に一から作った完全な架空ケースです。
不足情報を推測で補わず、「要確認」としてください。

【架空ケース】
ここに教材のケース文だけを貼る

次の順で回答してください。
1. 開始条件から完了条件までを、1行1動作の表へ分解する。
2. 各動作の入力、出力、担当候補、判断、例外、不足情報を書く。
3. 廃止、簡素化、通常の自動化、AI補助、人間判断の候補を理由付きで示す。
4. AIは草案・分類・候補整理までとし、高影響判断、外部送信、支払、削除、
   権限変更、対外的な約束は、担当部門・必要な専門家・権限者が判断する設計にする。
5. 個人情報、認証情報、機密情報を新たに作らない。
6. 通常例、境界例、例外例と、停止条件・手動代替の候補を示す。
```

### AI案との比較・修正表

| 論点 | 自分の初案 | AI案 | 採用／修正／却下 | 理由・確認先 |
|---|---|---|---|---|
| 手順 |  |  |  |  |
| 判断・承認 |  |  |  |  |
| 例外 |  |  |  |  |
| リスク・停止 |  |  |  |  |

AI案は正解ではありません。現行業務に存在しない手順、根拠のない時間・KPI、AIによる最終判断があれば修正または却下します。

### After案の記録項目

- 廃止・簡素化してから、通常の自動化とAI補助を選んだ順序
- AIが作る候補と、人が確認・判断・承認・実行する箇所
- 入力・出力の取扱い、権限、ログ、保存・削除
- 通常例・境界例・例外例、停止条件、手動代替
- Before / Afterの総時間、確認時間、品質、費用、残るリスク

少数の架空PoCで重大誤りが0件でも、安全の保証にはなりません。そのケースで問題が観測されなかった可能性を残し、非公開試行→限定利用→対象拡大の各段階に承認条件と継続監視を置きます。

## 演習1：事務業務の分解

### 架空ケース

総務担当が、毎月80件の備品購入申請を処理します。

```text
申請はメールと表計算で到着。品名、数量、希望日、部門、予算区分を確認。
不足があれば差戻し。社内カタログ掲載品は価格表と照合。
5万円以上、カタログ外、緊急申請は管理者承認。
承認後に購買台帳へ転記し、申請者へ結果を通知。
1件平均12分、差戻し率25%。金額と承認結果の誤りは許容しない。
```

### 自力課題

1. 12〜18動作に分けます。
2. 入力形式の統一で先に簡素化できる箇所を探します。
3. AIが候補を出せる箇所と、規則処理の方が安定する箇所を分けます。
4. 金額、承認、通知の人間確認を設計します。
5. 20件の架空申請を通常例・境界例・例外例へ分け、PoCを作ります。

> 自力で作成した後、対応する自己点検ガイドで根拠と修正点を確認します。

## 演習2：営業業務の分解

### 架空ケース

営業担当10名が、週に各8件の商談後処理を行います。

```text
商談メモは自由形式。顧客課題、質問、自社の約束、次回候補を整理。
お礼メールを作成し、CRMへ要点と次の行動を登録。
値引き、納期、個別仕様は上司または担当部門の承認が必要。
1件25分。約束の記録漏れとCRM入力のばらつきが課題。
```

### 自力課題

1. 商談前、商談中、商談後、承認、記録へ分けます。
2. 「顧客の発言」「営業の提案」「確定した約束」を分離する項目を作ります。
3. AIでメモ整理とメール草案を行う場合の入力禁止・最小化を決めます。
4. 値引き・納期・仕様をAIが確約しない制約と承認を設計します。
5. 時短以外のKPIを3つ決めます。

> 自力で作成した後、対応する自己点検ガイドで根拠と修正点を確認します。

## 演習3：教育業務の分解

### 架空ケース

教育担当2名が、新入社員向け研修を毎四半期更新します。

```text
社内規程の改訂を確認し、スライド、自力課題、振り返り、自習のポイントを更新。
各部門責任者が内容を確認。前回は古い規程が1枚残り、差替えが発生。
教材更新に合計16時間。AI利用は架空データでの草案のみ承認済み。
```

### 自力課題

1. 規程収集、差分確認、教材更新、専門レビュー、版管理、配布へ分けます。
2. AIに任せられる草案作業と、規程所有者が判断する作業を分けます。
3. 古い版を混ぜない管理方法を設計します。
4. 自力課題の成果物と行動目標が対応しているかのチェックを作ります。
5. 公開前の権利・個人情報・正確性レビューを割り当てます。

> 自力で作成した後、対応する自己点検ガイドで根拠と修正点を確認します。

## 演習4：IT運用業務の分解

### 架空ケース

社内IT窓口が月150件の障害・依頼チケットを扱います。

```text
件名と本文から、アカウント、端末、ネットワーク、業務アプリへ分類。
緊急度を確認し、既知FAQがあれば一次案内。解決しなければ担当班へ割当て。
パスワード、ログ、画面画像が本文に含まれることがある。
AIに本番システムの変更権限は与えない。重大障害は責任者が判定。
```

### 自力課題

1. 受信、秘密情報検出、分類、影響確認、FAQ検索、回答、割当て、記録へ分けます。
2. AIの分類候補と重大度の最終判断を分けます。
3. パスワード・APIキーを検出した場合の停止・失効・報告を作ります。
4. RAGを使う場合の文書版、権限、根拠表示を決めます。
5. 誤分類、重複チケット、サービス停止の手動代替を設計します。

> 自力で作成した後、対応する自己点検ガイドで根拠と修正点を確認します。

## 演習5：AI活用ポイントの発見

### 自力課題

演習1〜4から改善候補を各3件、合計12件抽出し、次の表で優先順位を付けます。

| 候補 | 頻度 | 1件時間 | 標準化可能性 | 誤り影響 | 検出容易性 | データ適合 | 導入負荷 | 推奨 |
|---|---:|---:|---|---|---|---|---|---|
|  |  |  | 高・中・低 | 高・中・低 | 高・中・低 | 可・条件・不可 | 高・中・低 | 今／PoC／保留／禁止 |

### 優先順位の原則

- 頻度・時間・標準化可能性が高い
- 誤りの影響が低〜中で、人が誤りを検出しやすい
- 教材の完全な架空データと、組織指定の承認済みツールで実施できる
- 下書き・候補提示から小さく始められる

高頻度でも、認証情報や高影響判断を扱うものを自動化候補にしません。

## 自分の業務への転用成果物

最後に、自分の業務から「安全に検討を始められる小さな1業務」を選び、1ページの転用案を作ります。これは実データをAIへ入力する演習ではありません。顧客名、社員名、案件名、実際の文章・数値・画面・ファイル・ログ・社内URLは書かず、ローカルの未共有Markdownまたは指定シートへ、非機密の業務メタデータだけを記入します。

| 項目 | 記入欄 |
|---|---|
| 業務の一般名・目的 | 例：定例報告の下書き。固有名詞は書かない |
| 開始・完了 | 何を受け取ったら始まり、誰の承認で終わるか |
| 頻度・時間 | 概算または幅。機密数値は書かない |
| 困りごと | 転記、待ち、ばらつき、検索等 |
| AI前に廃止・簡素化できること |  |
| AI補助の小さな候補 | 草案、分類、要約、確認質問等 |
| 人が判断・承認すること | 高影響用途はAIが材料整理まで |
| 情報の区分 | 絶対禁止／条件付き／通常利用候補／不明。内容そのものは書かない |
| 着手前の確認先 | 業務責任者、情報管理、法務、個人情報、IT等 |
| 架空テストの作り方 | 実在者・実案件を元にせず一から作る |
| テスト構成 | 通常例／境界例／例外例 |
| 成功・停止条件 | 時間だけでなく、品質・安全を含める |
| 段階展開・監視 | 非公開試行→限定利用。品質、苦情、事故等を監視 |

転用案をAIへ相談する場合も、自分または所属組織が用意した架空の置換ケースだけを使います。実データを使うPoCはこの演習の続きとして始めず、組織の正式な申請・審査へ渡します。この1ページと記入済みの[業務分析シート](../templates/business_analysis_sheet.md)を本演習の成果物とします。

## 総合自己点検ポイント

| 観点 | 完成した状態 | 改善が必要な状態 |
|---|---|---|
| 範囲 | 開始・完了が明確 | 業務の一部だけを根拠なく対象にする |
| 粒度 | 1行1動作 | 業務名のままで分解していない |
| 入出力 | 形式・機密・所有者を記録 | データの所在や機密性が不明 |
| 判断 | 根拠・責任者を明記 | AIへ一括して任せる |
| 例外 | 停止・相談・手動代替がある | 正常系しか設計していない |
| 改善順 | 廃止→簡素化→通常自動化→AIの順で検討 | 最初からAI製品を選ぶ |
| 効果 | 総時間・品質・リスク・費用を比較 | 時短だけで判断する |
| 承認 | 高影響操作ごとに権限者を置く | 最後に形式的な確認だけ置く |
| PoC | 架空データ、期待する状態、停止条件がある | 本番データ・本番権限から始める |
| PoCの解釈 | 通常・境界・例外を試し、0件の誤りを安全保証にしない | 少数例で誤り0件なら安全と判断する |
| 実務転用 | 非機密の業務メタデータで転用案を作り、正式審査へ渡す | 実際の業務データを研修ツールへ貼る |
| 説明 | 業務目的と判断軸で選択理由を説明 | 製品名だけで推奨する |

## 自己点検と1点修正

1. 自分の成果物と照合記録を先に完成させます。
2. [この演習の自己点検ガイド](../self-check/exercises/business_process_mapping_self_check.md)を開きます。

4. 誤りまたは改善点を最低1点修正し、`修正前／修正後／修正理由`を記録します。
5. ガイドと異なっても、元資料で説明でき安全条件を満たす場合は、成立する別解として理由を残します。
