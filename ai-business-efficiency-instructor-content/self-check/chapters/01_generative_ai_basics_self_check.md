# 01 生成AIの基礎：成果物例と自己点検

[元教材「01 生成AIの基礎」へ戻る](../../01_generative_ai_basics.md)

## 自己点検の進め方

1. このページを読む前に、自分の成果物を保存します。
2. 最初は各演習の「段階ヒント」だけを読み、自分で1回見直します。
3. 次に「一致必須」と「成果物例」を確認します。文章を同じにするのではなく、違いの理由を説明します。
4. 「危険な状態」に当てはまる箇所があれば、その箇所を優先して止めます。
5. 最後に改善点を1つだけ選び、成果物を修正して再保存します。

- 本書の成果物例は一例です。日常的な別の例や比喩でも、意味と注意点が正しければ成立します。
- クイックスタートと本章の演習で対話AIを実際に操作したことが前提です。保存済み出力やこの成果物例を読むだけでは完了になりません。
- AI出力は流暢でも正しいとは限りません。演習結果は必ず人が本文、元資料、利用目的に照らして確認してください。
- 架空データだけを使います。未公開情報、個人情報、認証情報などを実際のAIツールへ入力しません。
- 法律、医療、金融などの高リスク領域ではAIに最終判断をさせず、資格・権限を持つ専門家が確認します。
- モデル、上限、料金、データ利用条件などのツール仕様は変わるため、実施時点の最新の公式情報を確認してください。

## 演習0：会議メモを実務成果物へ変換する

### 段階ヒント

[クイックスタート](../../setup/participant_quickstart.md)で作成済みの議事録とタスク一覧を使います。同じ会議メモをAIへ再送しません。クイックスタートが未完了なら、先に一度実施してから戻ります。

この章で期待する記入例は次のとおりです。

> AIに任せた作業：箇条書きの会議メモを、見出し付き議事録と3列のタスク一覧へ整理する作業／人が確認した作業：決定3件、タスクの担当・期限3組、未決3件が元メモと一致し、未知の情報が追加されていないかを確認する作業

文章が異なっても、AIの役割を「整理・草案・形式変換」、人の役割を「事実照合・正式判断・利用判断」と分けられていれば成立します。初回草案のメモ帳保存やプロンプトの再実行は完成条件に含めません。

### 一致必須

| 区分 | 期待結果 |
|---|---|
| 会議情報 | 会議名は「架空AI研修運営改善会議」、開催日は「2026-07-08」 |
| 参加役割 | 研修責任者、研修運営担当、情報システム担当、情報セキュリティ担当 |
| 決定1 | 次回初心者研修は教材の完全架空データだけを使用する |
| 決定2 | 終了時チェックリストへのリンクを学習案内へ追加する |
| 決定3 | 会議終了時チェックリストを共有フォルダーへ置く |
| タスク1 | 学習案内の改訂／研修運営担当／2026-07-12 |
| タスク2 | 業務用アカウントのログインテスト／情報システム担当／2026-07-11 |
| タスク3 | 入力禁止情報一覧レビュー／情報セキュリティ担当／2026-07-10 |
| 未決1 | 録画可否、確認担当、期限は未決。法務確認が必要 |
| 未決2 | フォローアップ会の実施可否と日程は未決 |
| 未決3 | 次回会議の日付、時刻、会場は未決 |

### 成果物

この章で新たに作るのは、`AIに任せた作業／人が確認した作業`の役割分担メモです。クイックスタートの完成議事録とタスク一覧は参照用であり、同じプロンプトの再送や初回草案の別保存は求めません。

### 自己点検と改善例

| 一致必須 | 自分で確かめる点 | 危険な状態・改善例 |
|---|---|---|
| 完成成果物を根拠に振り返る | 実際に速くなった整理と、人が確認した項目を挙げたか | 一般論だけを書き、今回の成果物に触れていない |
| 未知の情報を補わない | 録画、フォローアップ会、次回会議に可否・担当・期限・日時・会場を作っていないか | 「おそらく研修運営担当」などと推測している |
| AIと人の役割を分ける | 整理・形式変換と、事実確認・正式判断を区別したか | 「AIが議事録を完成させた」としている |
| 同じ操作を繰り返さない | 作成済み成果物を比較に再利用したか | 同じ完成プロンプトを理由なく再送している |
| 安全に終了する | 指定保存先だけを使い、外部送信・公開をしていないか | 共有リンクを作る、実在データへ置き換える |

### 振り返り例

> AIは箇条書きを議事録と表へ整える作業を速くできた。一方、未決事項の担当や期限を自然に補う可能性があるため、元メモとの全件照合は人が行った。正式な議事録として使えるかを決めるのも人の役割である。

### 再挑戦のポイント

この演習の目的は製品操作の反復ではなく、AIに向く「整理・形式変換」と、人が担う「事実確認・正式判断」を、直前の体験から説明することです。うまく分けられなければ、成果物の各行へ「AI案」「人が元資料で確定」の印を付けてから書き直します。プロンプト変更の練習は第04章へつなぎます。

## 演習1：初心者向け言い換え

### 利用環境の準備確認

- 基本ツールは組織が指定した承認済み対話AIです。ChatGPTは選択肢の一例です。[対話AIアカウント準備ガイド](../../setup/chat_ai_account_setup.md)で、利用環境とデータ設定を確認します。
- 組織利用では管理者が発行・招待した業務用アカウントを使います。利用できない場合は正式窓口へ確認し、承認済み対話AIを利用できるまで演習を停止します。
- 個人学習では本人が利用条件を確認した個人アカウントを使えます。入力は教材内の架空データに限定します。

### 段階ヒント

まず「トークン」だけを、`定義→身近な例→注意点`の3文へ分け、対話AIに改善案を出させます。本文と一致する箇所、ずれる箇所を自分で印付けしてから残りの用語へ進みます。

### 実務演習

LLM、トークン、コンテキストウィンドウ、マルチモーダル、ハルシネーションを、それぞれ「定義・例・注意点」の3文で説明します。専門用語を別の専門用語だけで説明しないことが条件です。

### 成果物例

#### LLM

1. **定義**：大量の文章例から言葉の続き方を学び、質問や指示に合わせて文章を作る仕組みです。
2. **例**：業務では、メールの下書き、文章の要約、内容の分類などに使えます。
3. **注意点**：自然な文章でも事実が正しいとは限らないため、人が元資料と照合します。

#### トークン

1. **定義**：AIが文章を読むときに、文字、単語、単語の一部、記号などへ分ける小さな単位です。
2. **例**：長い資料ほどこの単位が多くなり、入力できる量や料金に影響する場合があります。
3. **注意点**：日本語の1文字が常に1単位になるわけではなく、数え方は使う仕組みによって変わります。

#### コンテキストウィンドウ

1. **定義**：AIが1回の処理で参照できる質問、会話、添付資料、回答などの範囲です。
2. **例**：作業机の広さにたとえると、机に置ける質問や資料の量に当たります。
3. **注意点**：範囲内に資料が入っても、重要箇所を正しく使える保証はないため、人が引用箇所を確認します。

#### マルチモーダル

1. **定義**：文章だけでなく、画像、音声、動画など複数種類の情報を扱えることです。
2. **例**：会議音声から文章案を作ったり、画像内の表を説明したりできます。
3. **注意点**：顔、名札、録音内容、画面通知なども渡る可能性があるため、権利、同意、個人情報、機密情報を入力前に確認します。

#### ハルシネーション

1. **定義**：AIが、もっともらしい誤情報や実在しない出典を作ることです。
2. **例**：存在しない社内規程の条文番号や、誤った統計値を自然な文体で示す場合があります。
3. **注意点**：AIへ聞き直すだけで正しいとは判断せず、公式発表や原資料など、発信元に近い情報で確認します。

### 自己点検と改善例

| 一致必須 | 自分で確かめる点 | 危険な状態・改善例 |
|---|---|---|
| 平易な定義がある | 初めて聞く人が別の専門用語を調べずに理解できるか | 専門用語を別の専門用語へ置き換えただけである |
| 身近な例がある | 業務場面または日常場面を想像できるか | 抽象的な説明だけで用途が分からない |
| 限界または注意点がある | 人が何を確認するかまで説明しているか | 「便利」「高性能」で終わっている |
| 本文と一致している | AIが加えた仕様値や製品固有情報を人が確認したか | 根拠を確認できない数値や機能を断定している |
| 全用語を説明できる | 定義・例・注意点の組が全用語にあるか | 一部の用語で注意点が欠けている |

### 自己点検

本文と1項目ずつ照合し、定義の正しさ、例の分かりやすさ、注意点における人間確認を見ます。AIが加えた仕様値や製品固有情報は、最新の公式情報を確認できなければ削除します。学習仲間がいる場合の相互確認は任意です。

### 振り返り例

> 「コンテキストウィンドウ」を机にたとえると量は伝わったが、机に置いた資料を必ず正しく読むわけではないという限界が抜けていた。人による引用確認を追加した。

### 成立する別解

- LLMを「文章の続きを作る非常に大きな予測装置」、コンテキストウィンドウを「作業机」などにたとえても構いません。
- マルチモーダルの例は、文書、画像、音声、動画のどの組合せでも成立します。
- ハルシネーションの確認先として、法令原文、公的統計、製品の公式文書などを挙げても成立します。

### 危険な状態と修正

- LLMを「何でも理解して答える知能」と説明する。
- トークンを「必ず1文字」または「必ず1単語」と断定する。
- コンテキストウィンドウが大きければ、全資料を正確に理解すると説明する。
- マルチモーダルを画像生成だけの機能とする。
- ハルシネーションを「AIが故意にうそをつくこと」と説明する。

### 再挑戦のポイント

別の専門用語で言い換えていた場合は、「その言葉を初めて聞く自分へ説明できるか」と問い直します。仕組みを厳密に説明することより、業務上の用途と限界を誤解なく伝えられることを優先します。

## 演習2：向き・不向き分類

### 利用環境の準備確認

- 組織が指定した承認済み対話AIと教材の架空ケースだけを使います。別の日に行う場合は、アカウント種別、組織承認、入力禁止情報を改めて確認します。
- 組織利用では管理者発行の業務用アカウントを使い、利用できない場合は演習を停止して正式窓口へ確認します。
- 個人学習では本人が利用条件を確認した個人アカウントを使います。

### 段階ヒント

「架空の社内イベント案内文」を例に、データの機密性、誤りの影響、誤りを人が見つけられるか、人間の責任という4軸を順番に当てはめます。対話AIに分類候補を出させ、AI案と自分の判断が違う箇所を先に探します。

### 実務演習

次を「AIに下書きを任せる」「補助利用のみ」「原則として人が判断」に分類し、理由、確認者、停止条件を書きます。

1. 架空の社内イベント案内文
2. 未公開決算数値の分析
3. 公開済み製品FAQの分類
4. 患者への治療方針の決定
5. 会議メモから決定事項候補を抽出

### 成果物例

| ケース | 分類 | 理由 | 確認者 | 停止条件 |
|---|---|---|---|---|
| 架空の社内イベント案内文 | AIに下書きを任せる | 完全な架空データで、日時や表現の誤りを人が見つけて修正しやすい | イベント担当者。公開時は日時、場所、対象者、連絡先を確認する | 実在する参加者情報が混入した、または開催条件を確認できない場合 |
| 未公開決算数値の分析 | 原則として人が判断 | 重要な機密情報であり、入力可否と分析結果の影響が大きい | 財務責任者、情報セキュリティ担当者。会計・開示判断は必要な専門家が確認する | 未承認ツールへの入力を求められた、権限・契約・利用範囲を確認できない場合 |
| 公開済み製品FAQの分類 | AIに下書きを任せる | 公開情報であり、分類結果を元FAQと照合しやすい。ただし、古い版や分類漏れは起こり得る | 製品担当者またはカスタマーサポート責任者 | 公開範囲や最新版を確認できない、または根拠のない内容が追加された場合 |
| 患者への治療方針の決定 | 原則として人が判断 | 誤りの影響が重大で、患者ごとの状態や専門判断が必要 | 担当医療専門職。AIは最終決定者にしない | AIだけで決定・説明・実施しようとした場合。利用を止め、医療専門職へ引き継ぐ |
| 会議メモから決定事項候補を抽出 | 補助利用のみ | 決定、提案、未決を混同する可能性があるため、候補抽出までに限定する | 会議の主催者、議長、各担当者 | 元メモと照合できない、未承認事項を決定扱いした、または外部送信しようとした場合 |

### 自己点検と改善例

| 一致必須 | 自分で確かめる点 | 危険な状態・改善例 |
|---|---|---|
| 判断軸を使って分類している | 業務名だけでなく、機密性、影響、検出可能性を説明したか | 「文章作成だからAI向き」など、作業名だけで決めている |
| 確認者が具体的である | 担当部署、役割、必要な専門性が分かるか | 「人が確認する」だけで責任者が分からない |
| 停止条件が具体的である | どの状態で利用を止め、誰へ引き継ぐかが分かるか | 高影響の判断をAIだけで続ける。利用を止めて修正する |
| 入力環境を区別している | 承認済み業務環境と一般向け・未承認環境を混同していないか | 機密情報を無条件で一般向けAIへ入力している |
| 条件で分類が変わることを説明できる | 追加情報により判断が変わる理由を言えるか | 分類名を絶対的な正解として扱っている |

### 自己点検

自分の分類と反対の分類を仮定し、成立に必要な追加条件を書きます。未公開決算、医療、外部公開など影響の大きいケースは、組織の担当者または専門家へ引き継ぐ境界を確認します。

### 振り返り例

> 公開済みFAQはすぐ使えると思っていたが、公開範囲と版が不明なら補助利用にとどめる必要がある。判断を変える情報は、最新版の所在と公開責任者である。

### 成立する別解（条件付き）

- 未公開決算数値の分析を「補助利用のみ」とする案は、組織が正式に承認した環境、契約、権限、入力範囲、ログ、人間による全件確認を説明できた場合に限り成立します。一般向け・未承認ツールへの入力は成立しません。
- 公開済み製品FAQの分類を「補助利用のみ」としても、公開範囲や版の確認が難しいという理由が具体的なら成立します。
- 会議メモの抽出を「AIに下書きを任せる」としても、「決定事項候補」と明記し、主催者が元メモと全件照合する条件があれば成立します。

### 危険な状態と修正

- 「文章作成だからAI向き」のように、業務名だけで分類する。
- データの機密性だけを見て、誤りの影響や検出可能性を考えない。
- 「人が確認する」とだけ書き、誰が何を確認するかがない。
- 「公開済み」なら内容も必ず正しい、最新版であると考える。
- 医療の論点を、プロンプトを詳しくすれば解決できると考える。

### 再挑戦のポイント

分類名より判断理由を重視します。同じ業務でも、入力データ、組織の承認環境、誤りの影響、確認者の能力によって分類は変わります。「どの条件が変わると分類も変わるか」を1文で説明します。未公開情報を未承認環境へ入力する案や、医療の最終判断をAIへ任せる案になっていたら、利用を止め、担当者・専門家へ引き継ぐ手順まで書き直します。
