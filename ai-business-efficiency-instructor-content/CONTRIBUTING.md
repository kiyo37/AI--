# コントリビューションガイド

この教材への改善提案ありがとうございます。本ガイドは、内容の正確性、安全性、初心者への分かりやすさ、研修での再現性を維持するためのルールです。

> **GitHub用語**：**Issue**は問題や提案を記録して話し合う項目、**ブランチ**は正式版へすぐ影響させず変更を分ける作業場所、**コミット**は変更をひとまとまりで記録すること、**Pull Request**はその変更を確認して正式版へ取り込んでもらう提案です。詳しくは[用語集](glossary.md#githubでの共同編集)を参照してください。

## 提案できる内容

- 誤字、リンク切れ、表記揺れの修正
- 初心者向けの説明・例えの改善
- 用語集への用語追加
- 完全な架空データを使った演習追加
- 講師メモ、確認問題、解答、採点基準の改善
- セキュリティ、プライバシー、公平性、アクセシビリティの改善
- AI製品・公的ガイドラインの更新
- Markdownの可読性、表、相対リンクの改善

大きな章追加、対象者変更、学習順序変更、ライセンス変更は、先にIssueで目的と影響範囲を合意してください。

## 変更前の確認

### 機密情報・個人情報

実在する会社、顧客、従業者、患者、応募者などの情報を、Issue、コミット、Pull Request、画像、演習データへ含めないでください。

次は特に禁止します。

- 氏名、メールアドレス、電話番号、社員番号など
- 顧客メール、会議音声、社内文書、契約、未公開数値
- パスワード、APIキー、秘密鍵、トークン
- 実システムのURL、内部構成、脆弱性情報

例は一から作った架空データとし、「架空」であることを明記してください。

### ライセンス

公開前にリポジトリ所有者が正式な`LICENSE`を選択します。選択肢は[ライセンス選択ガイド](LICENSE_GUIDE.md)を確認してください。ライセンス未確定の間は、外部からの本文提供を受け付ける前に、権利帰属と利用条件を所有者へ確認してください。

第三者の文章、図表、画像、問題集、商標などを無断でコピーしないでください。引用が必要な場合は、必要最小限とし、出典、利用条件、引用部分を明確にします。個別判断は法務・知財担当者や専門家へ確認してください。

## 変更の進め方

1. 既存Issueを検索します。
2. 大きな変更は、新しいIssueで目的、対象者、変更予定ファイル、リスクを提案します。
3. 1つのPull Requestは、原則として1つの目的に絞ります。
4. 変更理由と確認方法をコミット・Pull Requestへ記載します。
5. 製品・法令・公的資料の更新では、公式URLと確認日を記録します。
6. レビュー指摘へ対応し、必要なら教材、演習、解答、リンクを同時に更新します。

ブランチ名の例：

```text
docs/fix-rag-definition
content/add-customer-support-exercise
update/tool-information-2026-07
accessibility/improve-table-layout
```

コミットメッセージの例：

```text
docs: RAGの初心者向け説明を改善
content: 架空の問い合わせ演習を追加
fix: 3時間研修の時間合計を修正
```

## 教材の品質基準

### 対象者と学習目標

- プログラミング初心者でも読める言葉を使う
- 「理解する」だけでなく、観察・採点できる行動目標を書く
- 講師が説明するときの例、非例、注意点を含める
- 特定製品の操作説明だけで終わらず、業務目的と人間の責任へ接続する

### 各章の基本構成

本編章を追加・大幅変更する場合は、次の8セクションを維持します。

1. この章の目的
2. 学習ゴール
3. 本編解説
4. 実務での使いどころ
5. 講師メモ
6. 演習
7. 確認問題
8. まとめ

演習には、目的、所要時間、架空データ、手順、提出物、採点基準、解答例または評価観点を含めます。

### 初心者向け表現

- 専門用語には、その場の一言説明または[用語集](glossary.md)へのリンクを付ける
- 略語は最初に正式名称と意味を書く
- 用語を別の専門用語だけで説明しない
- 数式や実装が不要な章では、初心者が学ぶ範囲を明示する
- 一文を過度に長くせず、手順は番号付きリストにする

### 企業研修の安全性

次の原則を弱める変更は受け入れません。

- AI出力は必ず人が確認する
- 機密、個人情報、認証情報を安易に入力しない
- 外部送信、公開、重要判断、状態変更は人が承認する
- 法律、医療、金融、人事などは専門家確認を必要とする
- 製品仕様、規約、料金は最新の公式情報を確認する
- 事故時は停止、記録、報告、影響確認を行う
- 公平性、透明性、異議申立て、アクセシビリティを考慮する

### 製品・最新情報

製品情報を変更する場合は、次をPull Requestへ記載してください。

| 項目 | 記載内容 |
|---|---|
| 製品・機能 | 変更対象 |
| 公式URL | 製品・管理者・規約ページ |
| 確認日 | YYYY-MM-DD |
| 変更内容 | 以前の記述と新しい記述 |
| 影響 | 章、テンプレート、演習への影響 |

ブログ、SNS、AI生成回答だけを根拠に、製品仕様や法律上の説明を変更しないでください。

## Markdownの記述ルール

- 見出しは順番を飛ばさない
- リポジトリ内リンクは相対リンクを使う
- URLだけを置かず、リンクの意味が分かる文字列にする
- 表の前後に空行を入れる
- 投影用の表は原則3〜5列に絞る
- 横長ワークはA3横向き・表計算で使う旨を書く
- 色だけで正誤・リスクを区別しない
- 画像を追加する場合は代替テキストと権利情報を付ける
- コードブロックには可能な範囲で言語名を付ける
- 解答を折りたたむ場合は`<details>`と`</details>`を対応させる

### Mermaid図の記述ルール

- 図は、AIの仕組み、データの流れ、AIと人の役割、安全上の判断など、文章だけでは理解しにくい内容へ使う
- 講座の進行、学習ロードマップ、時間配分、単純な手順一覧は、原則として本文・番号付きリスト・表で示す
- GitHubで安定して表示しやすい`flowchart`や`sequenceDiagram`を優先する
- 1つの図へ情報を詰め込みすぎず、原則として主要ノードを3〜9個にする
- 色だけに意味を持たせず、ノード名や矢印のラベルでも関係を伝える
- ノード内の文を短くし、記号を多用するラベルは二重引用符で囲む
- 図の前に内容が分かるタイトルを置く
- 本編の図番号は`図{章番号}-{章内連番}`（例：`図8-2`）にそろえる
- 図の後に「図の見方」と「講師向け説明ポイント」を文章で付ける
- 図だけで安全性の例外を省略せず、人間承認や専門家確認を文章でも明記する
- Pull Request前にGitHub上の表示、矢印、分岐ラベル、文字切れを確認する

製品名、英字、記号は既存ファイルの表記へ合わせます。

## ファイル構成と命名

- 本編章：`NN_lower_snake_case.md`
- 補助教材：内容が分かる小文字の英字名
- テンプレート：`templates/`
- 演習：`exercises/`
- GitHub運用文書：リポジトリルートまたは`.github/`

既存ファイルを`docs/`へ移動する変更は、相対リンク、GitHub Pages設定、READMEとの重複管理を含めてIssueで合意してください。

## Pull Requestの確認項目

- [ ] 変更目的を一文で説明した
- [ ] 対象者と学習目標に合っている
- [ ] 実在の機密情報・個人情報・認証情報を含まない
- [ ] AI出力を人が確認する原則を維持した
- [ ] 専門用語へ平易な説明を付けた
- [ ] 法的・医療・金融等の個別判断を断定していない
- [ ] 製品情報には公式URLと確認日を付けた
- [ ] 演習データは完全な架空データである
- [ ] 確認問題と解答・評価基準が一致している
- [ ] 相対リンクが切れていない
- [ ] Markdownの表、コードブロック、折りたたみタグの開始・終了が対応している
- [ ] Mermaid図がGitHub上で表示でき、文章による説明も付いている
- [ ] README、用語集、関連テンプレートへの影響を確認した
- [ ] ライセンスと第三者権利を確認した

## レビュー基準

レビューは次の優先順位で行います。

1. 情報漏えい、高影響判断、誤情報、権利侵害などの安全性
2. 内容の正確性と公式情報への追跡可能性
3. 学習目標、解説、演習、評価の一貫性
4. 初心者への分かりやすさ
5. 講師が進行・採点できる具体性
6. 表、見出し、リンク、アクセシビリティ

安全性または正確性に未解決の問題がある場合、表現上の改善より先に修正します。
