# コントリビューションガイド

教材への改善提案を歓迎します。安全性、正確性、初心者への分かりやすさ、一人での再現性を維持するため、次のルールに従ってください。

GitHub用語が分からない場合は、[用語集](glossary.md#githubでの共同編集)を確認してください。

## 提案できる内容

- 誤字、リンク切れ、表記揺れ
- 初心者向けの説明・例え・図解
- 用語集への追加
- 完全な架空データを使う演習
- 段階ヒント、自己点検、成立する別解
- 個人学習・組織利用の2つの利用環境の改善
- セキュリティ、プライバシー、公平性、アクセシビリティ
- AI製品・公式情報の更新

対象者、必修順序、ライセンス、大規模な章追加は、先にIssueで目的と影響範囲を合意してください。

## 寄稿の権利と受付条件

投稿者は、Pull Requestの対象について、次の全てを確認します。

- 自分が作成したか、又は投稿に必要な権利者の許可を得ている
- 勤務先、委託先、共同作成者、第三者の権利や契約に違反しない
- Pull Requestを送信することにより、投稿部分を本リポジトリへ収録し、修正し、現行の[`LICENSE`](LICENSE)の条件で公開・提供するために必要な非独占的かつ無償の許諾を、リポジトリの保守者に与えることに同意する

投稿者は、上記の許諾に必要な範囲を除き、投稿部分の著作権を保持します。同意できない場合や権利関係が不明な場合は、Pull Requestを送信せず、権利上の許諾を与えない一般的な問題指摘が可能かどうかをIssueで確認してください。Issueに第三者の文章や画像を転載しないでください。

> [!IMPORTANT]
> この記載は法的助言ではありません。初回の公開・Releaseや外部からのPull Request受入前に、著作権者、公開権限、寄稿条件、許諾窓口を法務・知財担当者または専門家が確認してください。この確認が終わるまで、外部からのPull Requestは取り込まず、Issueによる提案だけを受け付けます。

## 公開してはいけない情報

- 氏名、メール、電話番号、社員番号などの個人情報
- 顧客メール、会議音声、社内文書、契約、未公開数値
- パスワード、APIキー、秘密鍵、トークン、MFAコード
- 社内URL、内部構成、脆弱性情報
- AIへ実際に入力した業務データや出力
- 自分の業務や会社を特定できる演習メモ

例は一から作った架空データとし、「架空」であることを明記します。重大な安全問題は公開Issueへ詳細を書かず、[セキュリティ方針](SECURITY.md)に従ってください。

## 変更の進め方

1. 既存Issueを検索する
2. 大きな変更はIssueで目的、対象者、変更予定ファイル、リスクを提案する
3. 一つのPull Requestを原則一つの目的に絞る
4. 教材、演習、自己点検、架空資料、リンクを一緒に更新する
5. 製品・法令・公的資料の変更では、公式URLと確認日を記録する
6. Markdown、相対リンク、表、コードフェンスを確認する

## 自習教材の品質基準

### 章の基本構成

1. この章の目的
2. 学習ゴール
3. 始める前の確認
4. 本編解説
5. 実務での使いどころ
6. 演習
7. 自己点検と再挑戦
8. 完了条件
9. まとめと前後ナビ

章冒頭には、前提、利用環境、使用ファイル、成果物、開始・停止条件を示します。

### 演習の学習ループ

1. 利用環境の準備確認
2. 手順付き練習
3. 自力で行う実務演習
4. 元資料を使う人間レビュー
5. 段階ヒント
6. 自己点検と成果物例
7. 違いの理由を記録
8. 一か所以上修正して再確認
9. 完了条件と次へのリンク

点数、配点、合否、固定時間は付けません。自己点検は唯一解として扱わず、次を区別します。

- 一致が必要な事実
- 成立する別解
- 危険なので停止する状態
- よくある失敗と戻る資料

### 一人で完了できること

- 他の学習者とのペア作業を必須にしない
- 配布担当者や口頭説明を前提にしない
- 必要な架空入力を`sample-data/`へ収録する
- 誤り分析・比較・トラブル切り分けに使う問題出力を`sample-outputs/`へ収録する
- 記入用ファイルを`workbooks/`へ収録する
- 自己点検を`self-check/`へ収録し、演習末尾から直接リンクする

ペアレビューや組織内レビューを追加する場合も、一人用経路を標準として残します。

### 初心者向け表現

- 専門用語は初出で一言説明し、必要に応じて用語集へリンクする
- 略語は最初に正式名称と意味を書く
- 一文を長くしすぎず、操作は番号付き手順にする
- コピーする範囲、保存ファイル名、期待する途中状態を明示する
- 失敗した場合の戻り先を示し、AIを利用できない場合は環境準備まで停止させる
- 製品画面の暗記ではなく、目的と確認事項を説明する

### 安全性

次の原則を弱める変更は受け入れません。

- AI出力は必ず人が元資料・公式情報と確認する
- 機密情報、個人情報、認証情報を教材演習へ使わない
- 外部送信、公開、書込、削除、支払、権限変更は実行前に人が承認する
- 法律、医療、金融、人事等の高影響判断をAIだけで確定しない
- 事故時は停止し、秘密値を再転記せず正式窓口へ報告する
- 公平性、透明性、異議申立て、アクセシビリティを考慮する
- 少数ケースの誤り0件を将来の安全保証にしない

### 製品・最新情報

製品情報を更新する場合は次を記録します。

| 項目 | 内容 |
|---|---|
| 製品・機能 | 変更対象 |
| 公式URL | 製品・管理者・規約ページ |
| 確認日 | YYYY-MM-DD |
| 変更内容 | 以前と新しい記述 |
| 影響 | 章、演習、セットアップへの影響 |

ブログ、SNS、AI生成回答だけを根拠に、製品仕様や法律上の説明を変更しません。

## Markdownのルール

- 見出しレベルを飛ばさない
- リポジトリ内リンクは相対リンクにする
- URLだけでなく意味が分かるリンク名を使う
- 表の前後に空行を入れ、原則3〜5列にする
- 色だけで正誤・リスクを表さない
- 画像には短い代替テキストと権利情報を付ける
- コードブロックの開始・終了を対応させる
- 長い章には章内目次または保存チェックポイントを付ける

### Mermaid図

- AIの仕組み、データの流れ、役割、安全判断など文章だけでは難しい関係へ使う
- 学習順序や単純な手順は番号付きリスト・表で示す
- 一つの図の主要ノードを原則3〜9個にする
- 色だけに意味を持たせない
- 図の後に「図の要点」を文章で付ける
- GitHub上で表示を確認する

## フォルダー

| 場所 | 内容 |
|---|---|
| ルート | 本編、入口、公開運用文書 |
| `setup/` | 利用準備 |
| `exercises/` | 実務演習 |
| `workbooks/` | 学習者の記入用ひな形 |
| `sample-data/` | 完全な架空元資料 |
| `sample-outputs/` | 誤り分析・比較・トラブル切り分け用の保存済みAI出力 |
| `self-check/` | 段階ヒント、成果物例、別解 |
| `templates/` | 業務設計のひな形 |
| `.github/` | Issue・Pull Request設定 |

## Pull Request前の確認

- [ ] 対象者と学習目標に合う
- [ ] 実在する機密情報・個人情報・認証情報を含まない
- [ ] 一人で最後まで完了できる
- [ ] 個人学習・組織利用の2つの利用環境がある
- [ ] AIの実操作、出力確認、修正、再確認が完了条件に含まれる
- [ ] 元資料との人間レビューがある
- [ ] 自己点検と再挑戦がある
- [ ] 関連する章、演習、架空資料、自己点検を同時更新した
- [ ] 専門用語へ平易な説明がある
- [ ] 製品情報に公式URLと確認日がある
- [ ] 相対リンク、表、コードフェンス、Mermaidを確認した
- [ ] ライセンスと第三者権利を確認した

提案内容の権利条件は、上記の「寄稿の権利と受付条件」、[`LICENSE`](LICENSE)、Pull Requestの説明を確認してください。
