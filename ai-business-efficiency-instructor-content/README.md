# AI業務効率化講師 実践教材

生成AIの操作方法だけでなく、**業務を分解し、AIに任せる作業と人間が判断する作業を設計できる講師**を育成するための日本語教材です。

初心者向けのAI基礎から、企業研修で必要になるセキュリティ、ハルシネーション、著作権、AIガバナンス、RAG、自動化、AIエージェント、研修設計、模擬登壇までを一続きで学べます。

> [!IMPORTANT]
> AI出力は下書きです。最終判断と責任は人間が持ちます。演習では架空データを使い、実在する機密情報、個人情報、パスワード、APIキー（外部サービスを利用するための秘密の鍵）などを入力しないでください。

> [!NOTE]
> **LLM（Large Language Model／大規模言語モデル）**は文章を生成するモデル、**ハルシネーション**はAIがもっともらしい誤情報を作る現象です。**RAG（Retrieval-Augmented Generation／検索拡張生成）**は関係資料を検索して回答材料にする仕組み、**AIエージェント**は目標に応じて許可されたツールを使う仕組みです。**AIガバナンス**は、それらを安全に使うための責任・ルール・監視・改善を指します。詳しくは[用語集](glossary.md)を確認してください。

## この教材について

この教材の中心は、特定のAI製品の操作ではなく、次の判断サイクルです。

1. 業務目的を決める。
2. 現行業務を作業・判断・例外へ分解する。
3. AI、通常の自動化、人間の役割を決める。
4. 情報、正確性、権利、公平性、運用リスクを確認する。
5. 小さく試し、時間・品質・重大誤りを測る。
6. 人が承認し、結果を記録して改善する。

「AIツールを選ぶ」より先に「何のための業務か」を確認します。AI導入後も、最終承認と改善責任は人間が持ちます。

プログラミング経験は不要です。表計算、メール、文書作成などの一般的な業務経験を想定しています。

## 対象者

- AI業務効率化講師を目指す人
- ChatGPTなどの生成AIを業務改善に活用したい人
- 非エンジニアへAI活用を教えたい人
- 社内のAI研修やガイドライン作成を担当する人
- 企業研修で、安全性と効果を両立して説明したい人

## クイックスタート

### 自習する場合

1. [00 コース概要](00_course_overview.md)で30日計画を作ります。
2. [用語集](glossary.md)を手元に置き、各章を推奨順に読みます。
3. 各章の演習と確認問題を実施します。
4. [業務分析シート](templates/business_analysis_sheet.md)で自分の業務を分解します。
5. [10 研修設計](10_training_design_workshop.md)と[11 登壇実践](11_instructor_delivery_practicum.md)で最終成果物を作ります。

### 社内研修で使う場合

1. 自社の承認済みツール、入力禁止情報、相談先を確認します。
2. 対象者と研修時間に合わせて必要な章だけ選びます。
3. 演習データを実在情報へ置き換えず、架空データのまま利用します。
4. 自社ルールと異なる記述は、自社の正式な規程・担当部門の判断へ合わせます。
5. 登壇前に製品仕様、法令、規約、リンク、画面を再確認します。

## 図解の見方

本編の図は、AIの仕組みや安全上の判断など、文章だけでは初学者が理解しにくい内容へ絞っています。講座の進行、学習計画、時間配分は、図にせず本文や表で確認します。図はGitHubが標準対応しているMermaid形式で記述しています。

各図は次の順で読むと、内容を追いやすくなります。

1. 図のタイトルで、何を理解する図か確認する。
2. 矢印の始点から終点へたどる。
3. 分岐では、矢印に書かれた条件を読む。
4. 図の直後にある「図の見方」で意味を確認する。
5. 講師は「講師向け説明ポイント」を使い、具体例や注意点を補う。

> [!NOTE]
> Mermaidに対応しないMarkdown閲覧環境では、図がコードとして表示される場合があります。その場合も学習内容が失われないよう、各図の直後に文章で要点を説明しています。研修スライドへ転載するときは、文字サイズと色のコントラストを確認し、図だけでなく口頭説明または代替テキストも用意してください。

## templates の使い方

`templates/`には、実務や研修設計で繰り返し使う記入様式を収録しています。元ファイルを直接上書きせず、案件・研修ごとにコピーし、版と確認日を記録してください。

| テンプレート | 用途 | 推奨する利用場面 |

| [業務分析シート](templates/business_analysis_sheet.md) | Before / After、役割、リスク、KPI（重要業績評価指標） | 第04章の演習・顧客ヒアリング |
| [AI利用ルールひな形](templates/ai_usage_policy_template.md) | 企業向け利用ルールの検討 | 第05〜07章の後。専門部門レビュー必須 |
| [3時間研修スライド構成](templates/training_slide_outline.md) | 研修の時間・内容・演習設計 | 第10章の総合演習 |
| [模擬登壇観察シート](templates/instructor_observation_sheet.md) | 講師の登壇・質疑・安全対応の評価 | 第11章の模擬講義 |

### テンプレート利用手順

1. 利用目的と対象者を決める。
2. 架空データまたは利用が正式承認された情報だけを使う。
3. `{ }`や空欄を自社・案件の条件へ置き換える。
4. 業務責任者、情報システム、セキュリティ、法務など必要な担当者が確認する。
5. 文書名、版、確認者、確認日、次回見直し日を記録する。

## exercises の使い方

`exercises/`は、AIの操作ではなく、入力判断、事実確認、業務分解、人間承認を練習するための演習集です。

| 演習集 | 内容 | 主な対象章 |
|---|---|---|
| [メール・議事録・報告書](exercises/email_minutes_report_exercises.md) | メール返信、クレーム、議事録、報告書、要約 | 03・06 |
| [教材作成](exercises/teaching_material_creation_exercises.md) | カリキュラム、スライド、問題、初心者説明 | 01・03・10 |
| [業務プロセスマッピング](exercises/business_process_mapping_exercises.md) | 事務、営業、教育、IT運用の業務分解 | 04・09 |
| [リスク判断](exercises/risk_judgment_exercises.md) | 入力可否、誤情報、著作権、個人情報、公平性 | 05〜07 |

### 演習の基本進行

1. 個人で初回判断を記録する。
2. 利用者、承認者、リスク担当などの役割で相互レビューする。
3. AI出力を元資料・評価基準と照合する。
4. 修正理由、停止条件、相談先を記録する。
5. 完成文ではなく、判断過程と人間の責任を発表する。

## 研修利用時の注意事項

### 必須事項

- 実在する顧客、従業者、患者、応募者などの情報を演習へ使わない
- 機密情報、個人情報、パスワード、APIキー、秘密鍵をAIへ入力しない
- 組織が承認したツール、アカウント、設定だけを使う
- AI出力を元資料と人が確認し、外部送信・公開・重要判断前に承認する
- デモで実メール送信、支払、削除、アカウント付与などを実行しない
- 通信・アカウント障害に備え、紙上演習や事前保存した出力例を用意する
- 録音・録画を行う場合は、通知、同意、保存期間、閲覧範囲を確認する

### 専門家確認が必要な領域

法律、個人情報、著作権、契約、医療、金融、採用、人事評価などは、教材だけで個別判断を完結させないでください。対象地域の最新法令、自社規程、契約を確認し、担当部門や有資格の専門家へ相談してください。

### 製品情報

AIツールの機能、料金、画面、利用規約、学習利用、保存期間、提供地域は変わります。登壇日を基準に最新の公式情報を確認し、スライドへ「確認日」を記載してください。

## リポジトリ構成と docs 方針

### 現在の推奨構成

このリポジトリはMarkdown教材が成果物そのものなので、**現時点では `docs/`へ移動せず、このディレクトリをGitHubリポジトリのルートにする**構成を推奨します。GitHubを開いたときにREADMEと番号付き章がすぐ見えるためです。

```text
ai-business-efficiency-instructor-content/  ← この場所で git init
├── .github/
│   └── pull_request_template.md
├── .gitignore
├── README.md
├── CONTRIBUTING.md
├── LICENSE_GUIDE.md
├── glossary.md
├── 00_course_overview.md
├── 01_...md ～ 11_...md
├── templates/
└── exercises/
```

### docs/へ移動する条件

GitHub Pages、MkDocs、DocusaurusなどでWebサイト化する場合は、次の構成を検討します。

```text
├── README.md                 # GitHub向け概要
├── CONTRIBUTING.md
├── LICENSE
├── docs/
│   ├── index.md             # Web教材トップ
│   ├── chapters/            # 00〜11
│   ├── glossary.md
│   ├── templates/
│   └── exercises/
└── mkdocs.yml               # MkDocsを使う場合
```

同じ教材をルートと`docs/`へ複製すると更新漏れが起きます。サイト生成を導入するまでは現在の一元管理を維持してください。

### GitHub公開前チェック

GitHub用語は、**Issue**が課題・提案の記録、**Pull Request**が変更取り込みの提案、**ブランチ**が変更を分けて作業する枝、**コミット**が変更履歴のひとまとまりです。詳しくは[用語集](glossary.md#githubでの共同編集)を参照してください。

- [ ] `ai-business-efficiency-instructor-content/`をリポジトリルートにした

- [ ] 正式なライセンスを選び、`LICENSE`を追加した
- [ ] 秘密情報・実在個人情報・内部URLが含まれないことを確認した
- [ ] READMEと全相対リンクを確認した
- [ ] GitHubのIssues（課題・提案）とPull Requests（変更取り込みの提案）を有効化した

