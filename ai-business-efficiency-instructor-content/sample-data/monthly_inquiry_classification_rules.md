# 月次問い合わせ分類基準（研修用・架空）

> この分類基準と[問い合わせ明細30行](monthly_inquiry_cases.csv)は、研修用に一から作った完全な架空データです。実在する顧客、問い合わせ、契約、障害とは関係ありません。

## 1. 基準の位置付け

| 項目 | 内容 |
|---|---|
| 基準名 | 架空問い合わせ分類基準 |
| 版 | 1.0 |
| 適用対象 | `monthly_inquiry_cases.csv`の30行 |
| 対象期間 | 2026年7月 |
| AIの役割 | 分類、複数論点、優先確認、根拠語句の**候補**を出す |
| 人の役割 | 元の1行とこの基準を照合し、最終分類、集計対象、報告表現を決める |
| 禁止事項 | AIによる原因・責任・返金可否・障害範囲の断定、外部送信、自動振り分け |

「候補」とは、AIが提案した未確定の結果です。文章が自然でも、人が確認するまでは集計へ使いません。

## 2. 主分類

1件につき主分類を1つ選びます。二つ以上の話題がある場合は、問い合わせ者が最後に求めている対応、または中心となる依頼を主分類にし、残りを副論点へ記録します。判断材料が足りなければ推測せず、`保留（情報不足）`にします。

| 主分類 | 簡単な意味 | 含める例 | 含めない例 |
|---|---|---|---|
| アカウント・ログイン | 認証や登録情報へ入るための手続き | パスワード再設定、ロック、登録メール変更 | 画面へ入った後の一般操作 |
| 申込・契約 | 利用開始、人数追加、プラン・契約条件の変更 | 新規申込、プラン変更、追加申込 | 解約、請求済み金額の確認 |
| 請求・支払 | 請求書、領収書、料金、支払・引落しの確認 | 請求書取得、二重表示、引落日 | プラン変更そのもの、解約手続きそのもの |
| 操作方法 | 正常に使えることを前提とした操作の質問 | 通知設定、絞り込み、初期設定 | エラー表示や画面停止 |
| 不具合 | 期待する操作を続けられない現象 | エラー表示、画面が閉じる・白くなる | 原因が分からない曖昧な相談 |
| 解約 | 利用終了の申込みや適用日の確認 | 解約手順、解約日、更新時の終了 | 解約後に表示された請求の確認 |
| 保留（情報不足） | 主分類を決める材料が足りない | 対象操作が不明、本文が空欄 | 材料があり複数分類で迷うだけのもの |

### 複数論点を扱う順序

| 状況 | 主分類 | 副論点 | 理由 |
|---|---|---|---|
| ログインできず、支払期限の扱いを尋ねる | 請求・支払 | アカウント・ログイン | 求めている最終回答が支払期限の扱いだから |
| 解約したいが、解約画面でエラーが出る | 解約 | 不具合 | 求めている最終結果が解約だから |
| プラン変更時の料金と手順を尋ねる | 申込・契約 | 請求・支払 | 中心となる手続きがプラン変更だから |
| 解約後に表示された請求の扱いを尋ねる | 請求・支払 | 解約 | 求めている最終回答が表示された請求の扱いだから |

副論点がない場合は空欄にします。複数論点だからといって、同じ問い合わせを主分類へ二重計上しません。

## 3. 優先確認候補

次のどれかが本文に明記されている場合は、`要確認`とします。それ以外は`通常`です。これは**担当者が先に内容を見るための候補**であり、緊急度、事故、障害、補償の確定ではありません。

| 条件 | この教材で見る表現 | 人が確認すること |
|---|---|---|
| 直近期限と利用不能が同時にある | 今日・明日が期限で、ログイン不能やエラーがある | 実際の期限、代替手段、契約上の扱い |
| 金銭の重複・解約後請求の申告 | 同じ利用料が2回、解約後の請求 | 元記録、決済状態、対応権限 |
| 複数端末へ同じ現象の申告 | 3台で同じエラー | 影響範囲、再現状況、正式な障害情報 |

AIには`原因はシステム障害`、`返金が必要`、`契約違反`などと断定させません。法律、契約、金銭、個人情報に関係する判断は、組織の担当部署または専門家へ確認します。

## 4. データ品質と集計対象

上から順に判定します。

| 状態 | 判定 | 集計での扱い |
|---|---|---|
| 問い合わせIDが空欄 | `ID空欄` | 同一案件か確認できないため、この演習では除外する |
| 同じIDが前の行にある | 後から出た行を`重複候補` | 前の行を残し、後の行だけ除外する |
| 本文が空欄 | `本文空欄` | IDが一意なら件数には含め、主分類は`保留（情報不足）`にする |
| 上記以外 | `正常` | 主分類を確認して集計する |

この教材では、`問い合わせID`が同じでも機械的に削除する前に、受付日、件名、本文が同じかを人が確認します。実務の重複処理は、自社の正式なルールと記録責任者の承認に従います。

## 5. 分類根拠の書き方

- 元の件名・本文にある短い語句を使う
- `〜と思われる`という原因推測を書かない
- 本文が空欄なら`本文空欄のため分類不能`と書く
- 複数論点なら、主分類と副論点の両方の根拠を示す
- 優先確認候補では、期限、金銭、影響台数など、該当条件をそのまま示す

良い例：`「今日が支払期限」「ログインできず」と明記`
避ける例：`認証サーバー障害が原因で支払えない`

## 6. 月次集計の固定条件

| 項目 | 条件 |
|---|---|
| 元データ行数 | 見出しを除く30行 |
| 集計対象 | IDがあり、後から出た重複候補ではない行 |
| 主分類の数え方 | 集計対象1件につき1分類。副論点は主分類件数へ加えない |
| 保留 | 件数と比率へ含め、確定分類とは分けて表示 |
| 優先確認 | `要確認`かつ集計対象の件数を表示 |
| 比率の分母 | 集計対象件数 |
| 報告で言えること | この架空データの件数、比率、確認が必要な状態 |
| 報告で断定しないこと | 増減傾向、原因、顧客全体の傾向、障害、責任、返金・契約判断 |

集計値が合わない場合は、AIに合わせず、元データ、重複・空欄、数式範囲、最終分類を順に確認します。
